# Home Assistant driver family UI review

Three independent reviewers examined Quick Setup, the shared Light and Switch
interface, and Home Assistant Connection with the optional Gesture Bridge. Quick
Setup was exercised in a local browser with simulated devices. The reviewers
inspected the driver and companion source, the Switch icons, and the user's
Composer screenshots. The findings below describe the original review. The
follow-up records the fixes and deployment.

## Quick Setup

- Keep room assignment and review within reach at the bottom of a long list. At
  756 × 605, the preview moves the first device from 365 to 193 pixels below the
  top. The selected-device bar uses 41 pixels. At 420 × 360 it wraps to 75
  pixels and leaves about 16 pixels of the first row visible on entry with
  devices selected. Reduce filter and header height at narrow widths.
- Keep keyboard focus visible above the footer. At 420 × 360, Tab reached four
  checkboxes obscured by the bar. At this width the visual order of room
  assignment and review also diverges from keyboard order. Recheck both Tab and
  Shift+Tab with devices selected and with the bar wrapped.
- Show what is preventing review beside its button. A missing room or invalid
  name disables it even when the affected device is hidden by a filter. Show
  which selections need attention and provide a way to reach them.
- Explain the scope of batch room assignment before the user applies it. It
  currently overwrites individually chosen rooms for every selected device,
  including filtered-out ones. Distinguish the editable Control4 name from the
  Home Assistant device name.
- Keep the two-step creation flow. Use the first action to describe the review
  and the final action to say how many drivers will be created. In the simulated
  review, Back and repeat preview sent zero apply requests. The final
  confirmation sent one. Back preserves edits but moves focus to search. Return
  focus to the previous action or the item needing attention.
- Keep progress and errors visible beside the action. In the 420 × 360 pane, the
  review button was at y=285 while its progress and simulated error were at
  y=1261. Focus fell to the page body and stayed there after the error. Announce
  progress during review and creation, then return focus to the recovery action.
  The completed results correctly receive focus.

## Light and Switch

- Preserve the working device while validating a replacement. The shared setup
  handler clears the active configuration and saves the pending choice before
  resolution succeeds. Failure leaves the old controls disconnected. Advanced
  manual entry also needs to validate a new value before discarding the working
  selection. Verify both paths with an unavailable replacement.
- Identify the current selection and its controlled target in the device picker
  so users can distinguish devices with the same name and room. A Light with
  only a connected Control4 target can already say “Change device” before a Home
  Assistant device has been chosen.
- Give the initial “Connecting” state a recovery action when the driver does not
  answer. Restore keyboard focus when a status change closes the picker. Show
  the recovery instruction alongside status in native Properties.
- Explain where app commands go when changing “Button behavior.” In buttons-only
  mode a healthy Switch is presented with the same Navigator icon as an
  unavailable device. The existing on, off and unavailable icons otherwise
  distinguish states by shape as well as color.

## Home Assistant Connection and Gesture Bridge

- Lead native Properties with connection status, Home Assistant address and
  access token. Place certificate and diagnostic controls in Advanced and give
  connection errors a next action. The user's screenshot confirms Quick Setup
  still lands first on CORE 1, despite XML declaration order.
- In the packaged guide, explain where to create a token, what a successful
  connection looks like, and when to open Quick Setup. Correct the connection
  reference's obsolete statement about device control.
- Make action names describe their scope and outcome. “Retry Selected Devices”
  acts on devices tracked by the connection. “Export Timing Summary” writes to a
  variable and prints output, which the label does not help the user locate.
- When a Gesture Bridge source changes, explicitly review the light or switch it
  will operate. The form prepopulates the previous source's target. On first
  run, name the next setup screen and offer legacy import when there are
  controls to import. This review covered the real companion checkout.

## Verification boundaries

Quick Setup measurements apply to the proposed browser layout. Composer tab
order is based on the installed layout in the user's screenshot. The actual
Navigator presentation and native rendering of proposed changes still need an
operator check. No live device was created or reconfigured by this review.

## Follow-up

Quick Setup now keeps room assignment, validation feedback and **Review
devices** at the bottom. Bulk assignment fills empty rooms and preserves
individual choices. The review summary names the link to Home Assistant and the
destination in Control4. Browser checks covered forward and reverse keyboard
navigation, filtered selections, errors, editing a preview and explicit
confirmation at four sizes from 320 × 300 to 756 × 605. At the smallest size,
the room controls and a validation message can occupy 103 pixels. Scrolling
reveals the remaining rows.

Light and Switch now check a replacement before clearing the current device. The
picker identifies the current choice and target, initial loading can be retried,
and the Switch has a distinct healthy buttons-only icon. Coordinator Properties
leads with connection status and keeps support settings under **Show advanced
settings**. The optional companion’s replacement form identifies the new source
and asks for its linked target. An independent reviewer inspected the native
Home Assistant form at desktop and phone widths.

CORE 1 acknowledged and verified the Connection and Switch updates. The suite
Light package was staged on the controller for Quick Setup. The Home Assistant
companion changes were tested in its checkout. Native Composer tab order and
Navigator appearance after deployment still need visual confirmation.

## Saved programming and Advanced settings

The programming review compared the current XML with all relevant pinned
packages and exercised the user-visible choices through the driver shim.

- **Home Assistant Connection.** Call Service retains the six original fields in
  their original order, including all three variable pickers. The saved step
  describes the action and target. Packaged help gives examples for fixed
  brightness and a Control4 variable. A failed action directs the user to Last
  action. The two diagnostic Actions state what they print and where it appears.
  Debug Print appears in Advanced.
- **Light and Switch indicators.** The six Light and four Switch programming
  commands retain their saved names and parameters. Each per-button summary now
  identifies the chosen button and setting. Buttons offered for color,
  brightness and behavior depend on their capabilities. The packaged guide
  explains color entry, supported brightness levels and how a renamed extra
  button remains identifiable.
- **Light indicators following a connected light.** Advanced offers LED Behavior
  when the selected hardware has applicable settings. LED Feedback Source
  appears for Follow Bound Device. Selecting this mode can fill the source when
  the connections lead to a single light. When paddles control different lights
  the user chooses the source. Device Setup rendered a shim-provided Bottom
  selection and wrapped the guidance below it at 756 × 605, 420 × 360 and 320 ×
  300\. Both selectors had accessible names, descriptions and sequential keyboard
  focus. A second pass used the connected Top indicator fixture to check saved
  On and Off colors at all three sizes. The palette showed Off, Green and Red.
  Save returned focus to the same indicator on success, rejection and timeout.
  Moving to another field while waiting preserved focus there. A disappearing
  indicator left a visible status message. The restored native Show/Hide
  advanced settings actions identify Properties as their destination.
- **Light effects and paddle gestures.** The Navigator Extras messages specify
  Effects and Effect, offer the light's own effect names, show the active effect
  or Select Effect and remove the picker when the light drops the capability.
  Shim tests exercised all 15 native combinations of Top, Bottom and Toggle with
  single, double and triple taps, hold and release. New projects receive the
  standard proxy triggers once. Extra gestures keep their descriptive names, and
  existing suite events retain their IDs for saved programming.
- **Button diagnostics.** Light and Switch use the same three read-only Advanced
  fields. Last Gesture identifies the event, Gesture Count starts at driver
  startup, and Last Sequence shows the wall control’s event number. Debug Mode
  explains where the 25 messages appear and how to start a new set. Browser
  checks at 756 × 605 and 320 × 300 confirmed the labels, values and help fit,
  and the Debug Mode selector is keyboard-accessible. The native Action now says
  Print device diagnostics to Lua on both families.
- **Restoring a saved Light.** Device Setup explains when it is checking the
  Home Assistant device and when it needs fresh button feedback. If the device
  cannot be confirmed, both the page and native Next step direct the user to
  choose it again in Device Setup. The normal-entry shim exercised a different
  device with the same name and a different registry record.
- **Correcting a manual device ID.** On both Device Setup pages, the rejected
  entry and its correction guidance appear together in Advanced. Browser checks
  at the three sizes above confirmed that Enter submits or retries the value,
  Tab moves on while a reply is pending, and a late error leaves focus where the
  user placed it. The accessibility tree included both the error and field help.
  A valid correction cleared the invalid state. The driver shim confirmed the
  active device and saved selection survived the rejected edit.

Browser screenshots and measurements are stored locally in
`.cache/programming-parity-ui-review/`. Composer must still verify command
labels, populated selectors, saved programming, keyboard access to the native
properties, and which tab opens first. Navigator must verify the effect picker
on a supported and unsupported light, as well as native paddle triggers on the
controller.

The Light’s native fallback picker now offers **Refresh Home Assistant devices**
and **Choose Home Assistant device**. Source review confirmed that browsing
leaves the saved choice intact, an unlisted saved choice appears as **Current
device (saved)**, and a failed refresh gives a next step. Advanced Properties
shows the discovery result and accepts a custom catalog sensor for names and
rooms. The Composer search dialog still needs a visual and keyboard check.

### Composer’s outer row on CORE 1, revision 2026111804

The installer wants one click from Composer’s own device Properties row to each
heading and a single merged Properties view. The supplied screenshots show the
Light’s standard keypad LED editor in Properties. Device Setup, driver
Properties, Actions, Documentation and Lua are one level down under Advanced
Properties. The driver Properties tab renders three rows. The Light Group
reference also places its custom page at that inner level.

The independent usability review found that an extra HTML tab row fails this
task. The
[Composer System Design guide](https://docs.control4.com/help/c4/software/cpro/dealer-composer-help/content/composerpro_gettingstarted/system_design_view.htm)
describes the native split. The
[Light V2 proxy reference](https://snap-one.github.io/docs-driverworks-proxyprotocol/#hide_proxy_properties)
documents a static switch for hiding proxy properties. Neither reference
documents promoting driver pages or merging the native editors. The outer-row
requirement remains open.

### Composer navigation and migration review

The Light Group screenshot places the standard light settings in the outer
Properties tab. Advanced Properties contains the native Settings, Properties,
Actions, Documentation and Lua tabs. Only Settings is declared as
`config/tabs/tab` in Light Group’s XML. Its Group, Lights, Scenes and Settings
links are HTML within that tab. Repeating this pattern would introduce an extra
navigation row. The reviewed DriverWorks XML reference describes protocol
properties, and the Composer guide identifies the outer Properties tab as the
location of settings common to a device type. Outer placement of a custom page
remains unverified for CORE 1 running 3.4.3.
[DriverWorks XML reference](https://snap-one.github.io/docs-driverworks-xml/) ·
[Composer Pro User Guide](https://docs.control4.com/docs/product/composer-pro/dealer-user-guide/english/revision/V/composer-pro-user-guide-rev-v.pdf)

Migration preview at 720 × 680 and staged relay transfer at 560 × 560 both fit
the visible pane. The revised preview distinguishes saving a plan from moving
connections. A fresh review determines which actions are available. After a
timeout, the page clears the old choices and returns focus to reopening the
review. Relay confirmation includes both device names and IDs, the direction,
and the number of affected connections. User verification in Composer remains
for the native confirmation dialog and actual relay cutover.

### Single-page Device Setup

Light and Switch were rendered in Chrome at 1000 × 700, 560 × 360 and 320 × 300
using the shared production page and a simulated Director. The single page adds
no navigation row beneath Composer’s tabs. The selected wall device, its
separate controlled light, connection status and **Change device** fit within
the first 208 pixels of the smallest pane. A direct selection suppresses a
duplicate name. A separate target with the same name keeps its **Controls**
label.

Both drivers passed keyboard checks for changing devices, canceling with Escape,
restoring focus to **Change device**, retrying a failed browse and opening
Troubleshooting. Selecting a radio button and canceling sent no selection
command. A 30-device catalog paginated ten at a time, and the action stayed
visible while reviewing a lower row. An unsupported indicator section stayed
hidden on Switch. Opening the page issued only read requests. Opening and
canceling an older-driver review required an explicit action.

The first narrow manual-ID error left the focused **Save device ID** button 22
pixels below the viewport. After the fix, the input and Save button sit side by
side. At 320 × 300 the button ends at pixel 220 and the error ends at pixel 259.
Typing an ID and leaving the field sent no save command. A rejected save kept
the previous device. The indicator source label now explains that the selected
button identifies the linked light. The Light help follows the revised page.
Screenshots and measurements are under `.cache/merged-ui-review/`. Composer’s
native tab placement, visual scaling and webview keyboard handling still require
the user’s controller check.

### Whole-driver task review

The single-page checks above cover the HTML controls. A separate comparison of
the original BP 106, prototype 1 and suite 2026111807 Light archives identified
a handoff blocker. The suite declares dimming, click and hold rates, and preset
On behavior while hiding the standard proxy settings editor. BP 106 declares a
dimmer and omits the hide flag. Prototype 1 sets the hide flag. The Group Light
example illustrates the available standard dimmer editor. The binary fixture
alone does not establish which settings Composer exposes for a dimming BP light.

The review remains open for tasks without a reachable authoring path or
fixture-specific observation. Qualifying a replacement requires the baseline
version, fixture capabilities, starting settings, user entry point, save/reopen
and observed effect on the same target. Screenshots establish placement.
Controller data establishes identity and feedback. Each review should name the
surface it verifies and list any lost tasks for the user's explicit decision.

### Change the small indicator on a Home Assistant wall switch

The current Device Setup page places **Indicator lights on the selected wall
switch** below the selected-device summary in the review fixture. The first
controls belong to the physical indicator. A Zooz ZEN76-shaped fixture shows
**Status LED**, its current color, supported brightness levels and when it
lights. A ZEN26-shaped fixture shows behavior alone. A five-channel ZEN32-shaped
fixture retains the individual channels and names its extended colors. The
shared Light and Switch pages were tested at 320 × 300 and 1000 × 700.

Choosing red and pressing **Apply** sent one change addressed to the selected
status indicator. Home Assistant's simulated acceptance left the previously
reported blue visible. Subsequent device feedback changed it to red. With
missing physical metadata, the page explains the missing settings. For a raw
entity without the helper, Troubleshooting and the device picker explain how to
set up HA Gesture Bridge and select the named wall switch. A selected physical
switch in device-only mode receives instructions to enable button reporting. The
older custom Control4 keypad editor has been removed. Control4 keypad colors
remain a separate task in the native light editor.

These results use the packaged page sources with simulated profile data. They
establish findability and command semantics. A physical Zooz change and the
resulting Home Assistant feedback still need verification together. Local
captures and per-scenario results are under
`.cache/merged-ui-review/zooz-results.json`.
